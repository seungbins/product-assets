# 버그바운티 스코프 문서 템플릿

근거: [`../program-improvement-recommendations.md`](../program-improvement-recommendations.md) 1번 항목 — 스코프 불명확성이 보상액보다 참여·품질에 더 큰 영향을 미침 (Akgul et al. 2023, Malladi & Subramanian 2020).

## ⚠️ 이 문서만으로는 게시할 수 없는 이유

아래 템플릿에서 실제 제품 아키텍처(배포 형태, API 엔드포인트, 파일 처리 경로 등)와 관련된 항목은 **제가 임의로 채울 경우 사실과 다를 위험이 커서** 의도적으로 빈칸으로 남겼습니다 — 이 저장소에는 각 제품의 소스코드나 기술 문서가 없고 커버 이미지·데모 영상만 있어서, 실제 아키텍처를 아는 사람(담당자)의 확인 없이 "API가 이렇게 생겼을 것"이라고 추측해서 쓰면 오히려 잘못된 스코프를 공개하는 위험이 더 큽니다. 아래 "필수 입력" 표시가 된 항목만 확인해주시면, 나머지(취약점 카테고리·제출 규칙·SLA 기본값)는 이미 연구 기반으로 확정해 뒀습니다.

| 항목 | 상태 |
|---|---|
| 취약점 카테고리, 제출 규칙, SLA 기본값 | ✅ 연구 기반으로 확정 완료 — 그대로 사용 가능 |
| 대상 버전/빌드, 실제 인스코프 URL·엔드포인트, 배포 형태 | 🔴 **필수 입력** — 담당자만 알 수 있는 사실이라 비워둠 |

`[제품명]`을 실제 제품명(scene_renderer / puppet_animator / bg_batch_kit / lora_recipe / shorts_converter)으로 바꿔서 사용하세요.

## [제품명] 버그바운티 스코프

**최종 수정일:** [YYYY-MM-DD]
**대상 버전/빌드:** [예: v2.3.0 이상, 또는 최신 stable 릴리즈]

### 인스코프(In-Scope) 대상 — 🔴 필수 입력

- [ ] 애플리케이션 자체: `[배포 형태 — 데스크톱 실행 파일 / 클라우드 서비스 / CLI 도구 등]`
- [ ] API/백엔드 엔드포인트: `[도메인·엔드포인트 목록, 없으면 "해당 없음"]`
- [ ] 모델/에셋 파일 처리 경로: `[사용자가 업로드하는 모델·프리셋·배경 이미지 파일을 파싱/로드하는 부분이 있다면 명시]`
- [ ] 배치 처리 파이프라인: `[대량 파일 처리 시 리소스/경로 처리 로직이 있다면 명시]`

> 위 4개 항목은 이 저장소에 없는 실제 아키텍처 정보가 필요해 채울 수 없었습니다. 나머지 섹션은 그대로 사용 가능합니다.

### 아웃오브스코프(Out-of-Scope)

- [ ] 소셜 엔지니어링, 피싱
- [ ] 물리적 접근이 필요한 공격
- [ ] DoS/DDoS, 무차별 대입(brute force) — 명시적 서면 허가 없이는 금지
- [ ] 제3자 인프라(클라우드 벤더, CDN 등) — 해당 벤더의 자체 프로그램으로 안내
- [ ] [제품별로 실제 아키텍처를 아는 담당자가 채울 것 — 예: 정적 에셋/데이터 번들 성격이 강한 `lora_recipe`라면 애초에 "취약점"보다 "안전하지 않은 콘텐츠/라이선스 오남용 신고" 쪽으로 스코프 성격 자체가 달라질 수 있음]

### 관심 취약점 카테고리 (제출 시 참고)

> 아래는 출발점입니다. 실제 제품 아키텍처에 맞게 추가/삭제하세요. AI 콘텐츠 생성 도구 특화 리스크는 배경 조사가 끝나는 대로 이 섹션에 구체 항목을 추가할 예정입니다.

| 카테고리 | 예시 |
|---|---|
| 원격 코드 실행(RCE) | 악성 모델/에셋 파일 로드 시 임의 코드 실행 |
| 경로 순회(Path Traversal) | 배치 처리 시 파일 경로 조작으로 임의 파일 접근 |
| 인증/인가 우회 | API 키/세션 관련 우회 |
| 리소스 남용 | 과금·GPU 자원을 비정상적으로 소모시키는 입력 |
| 정보 노출 | 사용자 업로드 콘텐츠·모델의 의도치 않은 노출 |
| 공급망 | 서드파티 의존성/모델 배포 채널 변조 |

### 제출 규칙

- 최초 발견자에게만 보상 (중복 제출은 보상 없음, 단 트리아지 판정 근거는 안내)
- 실 사용자 데이터에 접근하게 되는 경우 즉시 중단하고 신고
- 재현 스크립트/PoC 첨부 권장 (Laszka et al. 2016 — 신뢰도 신호가 트리아지 효율을 높임)

### 트리아지 SLA — ✅ 기본값 확정 (조정 가능)

- 최초 응답: **영업일 5일 이내** (Akgul et al. 2023 / Walshe & Simpson 2022가 지적한 최대 불만 요인이 응답 지연이므로, 소규모 프로그램이 실제로 지킬 수 있는 보수적 기본값으로 설정. 처리 인력 여유가 되면 더 단축)
- 판정 근거 공유: **모든 판정(Not Applicable/중복/Informative 포함)에 최소 1줄 사유 명시** — 근거 없는 판정이 헌터 이탈의 핵심 원인(Akgul et al. 2023)
